# Connections and release gates

## OpenAI
OpenAI is not connected. `OPENAI_API_KEY` and `OPENAI_MODEL` configure the server-side extraction action. It authenticates, reserves workspace and global daily quotas, validates structured output and source quotes, and uses timeouts. Each analysis may make two model requests: extraction and a cited draft. The database migration and live provider path still require integration testing; the schema does not prove accuracy or factual grounding.

## Gmail MCP
Gmail remains disconnected behind the PRD access and compliance gate. A read-only adapter targets the fixed Google Gmail MCP endpoint and exposes only search_threads, get_message and get_thread; selected-message and owner authorization are enforced by database-backed policies. PKCE/state, AES-GCM credential encryption, one-time database attempts, compare-and-set refresh, and fail-closed revocation helpers are implemented and locally tested. Owner-only, disabled-by-default OAuth start, callback, and disconnect routes are implemented with one-time state and a vault. An owner can explicitly search and select a message for import when all gates are enabled. Imports retain plain text only and become eligible for cleanup after 30 days; actual deletion requires a working scheduled worker. Live token exchange, Google MCP response compatibility and hosted retention have not been verified. The vault migration has not been applied to hosted Supabase. Do not connect it until Preview access, scopes, OAuth, encryption, revocation, selection, and policy checks are implemented and verified with a test identity. No Gmail write or send operation is implemented. Login to Relay does not grant Gmail access.

## Sandbox CRM
The sandbox workflow stores tickets and approvals in the Relay database. A session-authenticated REST action endpoint and a first-party, in-memory MCP server/client delegate to the same role-checked database RPC. They have not yet been tested end to end against hosted Supabase. A separate local synthetic CRM and reconciliation path are implemented but hosted integration remains unverified. This is not a third-party CRM connection.

## Migrations
The first migration was applied manually. The subsequent migrations are pending and have not been applied or tested. Before applying, review their access controls and run cross-user authorization, concurrency and recovery tests. Do not deploy or use real customer data until the release blockers in the PRD are satisfied.

## Durable jobs (disabled)
A queued path and Inngest handler are implemented but disabled by default. It requires the database migrations, server-only service role key, Inngest event/signing keys, and explicit `RELAY_ENABLE_DURABLE_JOBS=true`. The worker rechecks stored authorization and executes an idempotent database transaction. Queueing and event dispatch are separate: dispatch failures leave a queued job for investigation. A loopback-only synthetic CRM, database-backed dispatch store, reconciliation adapter and disabled worker path are implemented. Local tests exercise the database and HTTP path together; the hosted worker and live Supabase remain unverified.

Do not enable or deploy this worker yet. Inngest 4.26.2 is pinned with an npm override resolving its Zod dependency to 4.6.7, outside Inngest’s declared version range. This removes the reported high-severity version finding in the current audit; five moderate findings remain. Local tests, build and SDK introspection pass. A local Inngest Dev Server delivered a synthetic queued event to the worker and a synthetic Supabase-shaped RPC returned success; a second event with the same job ID caused no second run. This did not exercise actual Supabase or hosted signing, retries and recovery. Reassess the override when upgrading Inngest. Never expose a Supabase service role key to a browser.

## External write reconciliation design
`lib/crm/reconciliation.ts` defines a fail-closed adapter contract: claim before dispatch, never automatically resend after a claim, reconcile using the provider action ID, and accept a terminal outcome only for the approved payload hash. Storage must implement atomic claiming and monotonic terminal-state transitions. The loopback sandbox implements idempotent receipts. A service-role worker uses the persistent dispatch store and adapter, and a local test exercises an approved database action through HTTP with a lost response. The path is disabled pending security and hosted integration review. Remote network authorization and hosting are not implemented. Confirmed external success attempts to synchronize the local ticket and action atomically; if the local status conflicts, the UI reports that the external update succeeded but local review is needed. The SQL migration is not applied to the hosted project.

Gmail OAuth requires explicit `RELAY_ENABLE_GMAIL=true` and `GMAIL_ACCESS_REVIEWED=true`, a Google OAuth client, fixed callback URL, encryption key, server-only Supabase service role key, and the pending database migration. These flags do not establish compliance. Do not enable before the Google restricted-scope review and hosted security testing. If token exchange succeeds but credential storage fails, the callback attempts remote revocation but cannot prove the grant was revoked when Google is unavailable; the user is directed to review Google account permissions.

Gmail import additionally requires `RELAY_ENABLE_GMAIL_IMPORT=true`, `GMAIL_RETENTION_VERIFIED=true`, and a configured durable worker. These flags are operator assertions, not proof that cleanup is running. Keep them disabled until the worker dependency override is reviewed and scheduled deletion has been verified in the deployed environment. Imported content is workspace-visible and may be sent to OpenAI if a user explicitly requests analysis.

Google setup prerequisites (checked against [Google Gmail MCP setup](https://developers.google.com/workspace/gmail/api/guides/configure-mcp-server)): Developer Preview membership, a Google Cloud project with both Gmail API and Gmail MCP API enabled, an OAuth consent screen and authorized test user, a web OAuth client with the exact Relay callback, and Google Auth Platform’s AI-powered-agent setting on that client. Relay requests only `gmail.readonly`; do not add compose permission for this read-only flow. Google may require restricted-scope verification or a security assessment before broader use. These prerequisites and a live connection have not been verified.

Worker HTTP POST/PUT bodies are limited to 256 KiB before the SDK parses them, including when no Content-Length is supplied. This is defense in depth, not proof the SDK is safe; verify the limit against real Inngest callbacks before enabling the worker.
